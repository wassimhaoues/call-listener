# Backend Service

The backend is an ES-module Node service in `Call_listener_Backend/server/`. `server/index.js` starts Express and an independent `ws` server. Use `server/core/logger/` for structured, rotating logs; application logs are written under `logs/`.

## HTTP API

| Method and path | Purpose |
| --- | --- |
| `GET /health` | Returns service and Redis client status. |
| `POST /auth/token` | Accepts `{ "app_id", "device_id" }`; validates both, returns `{ "token", "expires_in" }`, and sets the `call_token` secure cookie. |
| `GET /auth/me` | Validates `call_token` and returns its JWT claims. |
| `POST /ws-ticket` | Requires a valid `call_token` cookie. Returns `{ "ticket", "expires_in" }` (`Cache-Control: no-store`): a short-lived, single-use WebSocket ticket bound to the cookie's `app_id` and `device_id`; see [Authentication](#authentication). |
| `GET /models` | Requires a valid `call_token` cookie. Returns the allowlisted model catalog `{ provider, defaultModel, source, fetchedAt, models: [{ id, name, contextLength, pricing, availability, isDefault }] }`. |
| `POST /preparation/brief` | Requires a valid `call_token` cookie. Generates a model-backed preparation brief from `{ context, model?, language? }`; see [Preparation brief](#preparation-brief). |

Malformed JSON bodies get `400 { "error": "invalid_json" }` and oversized bodies `413 { "error": "payload_too_large" }`.

## Preparation brief

`POST /preparation/brief` is an explicit candidate action (the desktop "Improve with AI" button); the local deterministic brief stays the default and fallback. Code: `services/preparation/` (`preparationBrief.js` prompt, parsing, and service; `preparationLimits.js` rate and budget; `configuredPreparation.js` wiring from `CONFIG`, injected into `createApp({ preparationBrief })`).

- **Request.** `context` must be a `version: 1` candidate context validated by `contracts/interviewContext.js` (legacy payloads and invalid contexts → `400 invalid_context`; other versions → `400 unsupported_context_version`). `model` (or else `context.settings.model`) must be in `OPENROUTER_ALLOWED_MODELS` (`400 unsupported_model`); omitted means the server default. `language` is `fr` or `en` and defaults to `context.settings.language`. Other malformed fields → `400 invalid_request`. The route accepts bodies up to 256 kB.
- **Evidence IDs.** `A<n>` is the n-th `candidate.achievements` entry and `E<n>` the n-th `evidence` reference (1-based, request order). The desktop client maps the IDs back with the same rule.
- **Prompt.** The system prompt holds the rules; candidate and job text travel only as JSON string values inside a `<candidate_data>` block (angle brackets escaped as `<`/`>`, so pasted text cannot close the block). The model is told the block is untrusted data, to use only the supplied facts and evidence IDs, and to list requirements without evidence in `missingEvidence` instead of inventing experience. The pasted CV text is never part of the context.
- **Response.** `200 { brief, model }` with `Cache-Control: no-store`, where `brief` is `{ introduction, starExamples: [{ requirement, evidenceIds, situation, task, action, result }], practiceTopics, questionsToAsk, missingEvidence }`. The model's JSON is validated with zod (introduction ≤ 1,500 chars; ≤ 5 STAR examples with ≤ 6 IDs each; ≤ 8 topics; ≤ 6 questions; ≤ 6 missing-evidence notes; each string bounded). Unknown evidence IDs are dropped, and a STAR example left with no approved evidence is removed. An invalid answer gets at most one repair call (only while budget remains); a second invalid answer, a provider error, or a timeout returns `502 preparation_failed` without provider details.
- **Cost controls.** Output is capped at `PREPARATION_MAX_OUTPUT_TOKENS` (default 2000) and each call at `PREPARATION_REQUEST_TIMEOUT_MS` (default 20000). Every call, including a repair, is charged against a per-installation daily budget `PREPARATION_DAILY_BUDGET_USD` (default 0.50; `0` disables the feature) priced per model (see [Per-model pricing](#per-model-pricing)), using reported usage or the conservative `ceil(chars / 4)` estimate. The Redis key `prep:budget:<sha256(device_id) prefix>` expires 24 hours after its first charge. Before each call (including a repair) the worst-case cost — estimated input plus the full output cap, at the requested model's price (the default model's when none is requested) — is reserved atomically with `INCRBYFLOAT`; a reservation that would pass the ceiling is rolled back and the request returns `429 preparation_budget_reached` without contacting the provider. When the call finishes, the reservation is settled to the reported (or estimated) usage; a failed or aborted call keeps only its estimated input cost. Concurrent requests therefore cannot jointly exceed the daily ceiling. Requests are rate-limited to `PREPARATION_RATE_LIMIT_PER_MINUTE` (default 3) per installation in a fixed 60-second window (`prep:rate:<hash>`), counted before validation → `429 preparation_rate_limited`. The provider request is aborted if the client disconnects. Logs record counts only, never candidate, job, or brief text.
- **Groq mode.** With `AI_PROVIDER=groq` the route returns `501 preparation_unavailable`: the Groq rollback adapter cannot cap output tokens, report usage, or honour a model choice, so it cannot be held to the budget.

## Model catalog and selection

`OPENROUTER_ALLOWED_MODELS` (comma-separated OpenRouter model IDs, at most 20) is the only source of selectable models; it defaults to `OPENROUTER_MODEL` alone and startup fails if it omits `OPENROUTER_MODEL`. `services/ai/modelCatalog.js` enriches the allowlist from OpenRouter's public `GET /api/v1/models` list (no key sent) with an in-memory cache (`OPENROUTER_CATALOG_TTL_MS`, default 10 minutes) and a 3-second lookup timeout. Models absent from the upstream list are returned with `availability: "unavailable"`; when the lookup fails, every allowlisted model is returned with `availability: "unknown"` and the lookup is retried after a minute. Stale data is served while a refresh runs, so the endpoint never blocks on OpenRouter after the first lookup. Upstream models outside the allowlist are never exposed. In `AI_PROVIDER=groq` mode the catalog is empty.

The candidate's choice travels as `settings.model` in the session context. The WebSocket handler rejects any model outside the allowlist (and any explicit model in Groq mode) with `{ "error": "unsupported_model" }` and keeps the previous session context. The selection is read from the session context for each generation, so a new context message changes the model for the next request only; an in-flight request keeps its pinned model. There is no cross-model fallback.

### Per-model pricing

Every budget (interview, preparation, and the evaluation cost guard) prices each call with the model that served it, from one price table:

- **`OPENROUTER_MODEL_PRICES`** (optional) is a JSON object keyed by OpenRouter model ID, prices in USD per million tokens:

  ```json
  { "anthropic/claude-sonnet-4.5": { "input": 3, "output": 15 }, "openai/gpt-5.6-luna": { "input": 0.2, "output": 1.2 } }
  ```

  The prices above are illustrative; configure the approved current rates. The value is parsed by `server/config/modelPrices.js`: valid JSON object, at most 50 models and 16 384 characters, model IDs in the allowlist format, each entry exactly `input` and `output`, each a number from 0 to 10 000. Startup fails on any violation; error messages never echo the raw value. Entries for models outside the allowlist are allowed (for example a dated model ID OpenRouter reports as served).
- **Coverage.** With `AI_PROVIDER=openrouter`, every model in `OPENROUTER_ALLOWED_MODELS` must have a price, or startup fails with `OPENROUTER_MODEL_PRICES has no price for allowlisted model(s): …`. Only the default model (`OPENROUTER_MODEL`) may omit its entry; it then uses `OPENROUTER_INPUT_USD_PER_MILLION_TOKENS` / `OPENROUTER_OUTPUT_USD_PER_MILLION_TOKENS` (defaults 0.2 / 1.2), so a deployment with only those two variables and no extra allowlisted models behaves exactly as before. A table entry for the default model wins over the pair.
- **Which price is charged.** The OpenRouter adapter reports the model with usage: `onUsage(usage, { inputChars, outputChars, model, actualModel })`, where `model` is the pinned (selected) model and `actualModel` the model OpenRouter reports in the response, or `null`. `services/ai/modelPricing.js` (`priceFor(modelId)`, `resolve(basis)`) charges the actual model when it is in the table, then the selected model, then the default model. An unpriced actual model that differs from the selection is logged once (model ID only).
- **Catalog cross-check.** After each successful catalog refresh (and once at startup in OpenRouter mode), the server compares the configured price of each allowlisted model with OpenRouter's catalog price and logs a warning when the configured input or output price is lower (once per model and catalog price). Catalog prices are only a check; they are never used for billing.

## Session context, intro, and budget

- **Context versions.** `contracts/interviewContext.js` accepts `version: 1` candidate contexts and legacy `caller`/`me` payloads (no `version` field). Any other declared `version` (for example `2`, `"1"`, or `0`) is rejected with `{ "error": "unsupported_context_version" }`; nothing is stored, no intro is generated, and the previous session context stays in effect.
- **Intro lifecycle.** Each accepted context starts one introductory suggestion through `StreamManager.beginIntroGeneration()`, which gives the request an `AbortController`. A newer accepted context supersedes (aborts) an in-flight intro, and `{ "end": true }` or socket close aborts it too. Aborted or late intros are never sent; a context received after `end` stores the context but starts no intro.
- **Evidence bound.** Prompts carry at most three evidence references. `evidenceSelector.js` returns the top three matches for the latest interviewer turn. When the latest turn matches nothing (typically a short follow-up such as "What did you change afterwards?"), it scores the preceding exchange instead: up to the five previous history lines, excluding assistant suggestions. When that also matches nothing, it falls back to the first three approved references in order. `promptBuilder.js` applies the same cap to intro prompts.
- **Budget accounting.** `interviewBudget.js` prices reported usage at the price of the model that served the reply (see [Per-model pricing](#per-model-pricing)); the Redis field `lastPricedModel` and the `model` returned by `recordUsage` name the priced model. When the provider omits a token count, the budget charges a conservative estimate instead of zero: `ceil(chars / 4)` tokens for system prompt plus history (input) and for the reply (output). The OpenRouter adapter passes these character counts, with the model IDs, as the second `onUsage(usage, { inputChars, outputChars, model, actualModel })` argument. The record is marked estimated (`recordUsage` returns `estimated: true`; Redis field `lastUsageEstimated`), and a warning is logged with token counts and the session ID only, never transcript or prompt text.
- **Streamed suggestions (opt-in).** A client that lists `"stream"` in `context.capabilities` gets live suggestions as generation-ID-tagged events (see [WebSocket protocol](protocols/websocket.md#streamed-suggestions)). `contracts/interviewContext.js` validates the list (`parseClientCapabilities`: at most 8 names of 1–32 characters; unknown names ignored); capabilities are never stored with the context or sent to a model. The latest accepted context decides, and each generation pins the setting when it starts. For a streaming generation, `StreamManager` passes an `onToken` callback through `interviewWorkflow.js` to the reply generator. The OpenRouter adapter then calls the LangChain model's `.stream()` (with `streamUsage: true`) instead of `.invoke()`, under the same abort signal and request deadline. It forwards text deltas only, never reasoning, and stops at the first abort. Usage is the sum of the chunks' `usage_metadata` (falling back to a chunk's raw `response_metadata.usage`), with the same estimate fallback. Without `onToken` the adapter makes the single `invoke` call as before. The Groq rollback adapter ignores `onToken` and returns the final reply only. `StreamManager` coalesces deltas and sends them at most every `STREAM_FLUSH_MS` (50 ms), flushes the tail before `done`, and drops buffered text once the generation is superseded, aborted, ended, or closed. The latest-question-wins scheduler is unchanged. The introductory suggestion is not streamed.

## Response actions

`{ "action": { "type", "generationId" } }` asks for `regenerate`, `shorten`, `expand`, or `clarify` on the current suggestion ([protocol](protocols/websocket.md#response-actions)).

- **Validation.** `contracts/candidateAction.js` validates the frame with a strict zod schema (known type, 1–64 character ID, no extra fields); a malformed frame is `Invalid message`. `messageHandler.js` passes a valid one to `StreamManager.requestAction()`, which returns either nothing (queued, or ignored after `end`) or the error payload to send.
- **Targeting.** `StreamManager` tracks the current interviewer question (its text, its latest final answer, and an action count) and the latest generation sent to the client. An action must name that generation, and it must still belong to the current question; otherwise it is rejected as `stale_generation`. `shorten` and `expand` also need a completed answer (`no_final_answer`). Completed `answer`, `regenerate`, `shorten`, and `expand` outputs become the question's latest answer; `clarify` output does not.
- **Scheduling.** An accepted action is queued as a new request in the latest-question-wins scheduler. Every queued request (question or action) bumps `requestVersion`, so the generation in flight is aborted and sends nothing further, and a newer question supersedes an action the same way. Each generation gets a new ID and a `kind` (`answer` or the action type) that is reported to clients that receive IDs (`stream` or the `actions` capability).
- **Cost controls.** Actions are charged to the interview budget like answers: `requestAction()` checks `Budget.canGenerate()` first (answering `interview_budget_reached`), and the generation records usage as usual. Accepted actions are limited to one per `ACTION_MIN_INTERVAL_MS` (1,500 ms; `rate_limited`) and `MAX_ACTIONS_PER_QUESTION` (5; `question_limit_reached`), which resets with each new interviewer question. Rejected actions make no model call. The 800 ms reply cooldown applies to actions too.
- **Prompts.** `interviewWorkflow.js` carries the action as `mode`, `question`, and (for `shorten`/`expand`) `previousAnswer`. Evidence selection uses the question text, so an action sees the same evidence as the answer it reworks. `promptBuilder.js` keeps the candidate system prompt (candidate evidence only, missing evidence stated) and appends a "Candidate request" block: the action's task, a rule that the quoted values are untrusted data, and the interviewer question and previous answer as JSON-encoded strings (bounded to 2,000 and 4,000 characters). `shorten`, `expand`, and `clarify` replace the answer-length format with their own; `regenerate` keeps it. Legacy contexts get the French action block.
- **History.** Action outputs are not pushed to the chat history, so later questions see the original conversation.
- **Resume.** Action messages are sequenced and replayed like any other. On disconnect, an action in flight is reported `failed` with `reason: "disconnected"`, and an action still queued is answered `action_rejected` / `disconnected`; neither is re-run.

## Unsaved debrief

A client that lists `"debrief"` in `context.capabilities` may end with `{ "end": { "debrief": true } }` to receive one review of the interview ([protocol](protocols/websocket.md#unsaved-debrief)). Nothing is stored.

- **Flow.** `messageHandler.js` parses `end` with `parseEndRequest` (`contracts/interviewReview.js`: `true` or a strict `{ debrief?: boolean }`). For a debrief end it calls the `beginEnd` lifecycle hook (an abort signal), `StreamManager.closeAll()` as for a plain end, then `generateDebrief({ sessionId, signal })`, sends the `{ debrief }` result if the signal has not aborted, and finally `onEnd` (the usual purge). Without the capability, or for `{ "end": true }`, the old path runs unchanged. Further `end` frames while the debrief is prepared are ignored.
- **Socket close.** `sessionManager.beginEnd(session)` marks the session as ending. `disconnect()` aborts that signal and purges the session (no resume window, even for resume-capable sessions).
- **Generation.** `services/interview/debrief.js` (`createDebriefGenerator`, wired in `connectionHandler.js`) reads the stored history and context. Interviewer (`caller`) and candidate (`you`) lines form the transcript; `assistant` suggestions are passed in a separate `aiSuggestions` list that the instructions say are not the candidate's words. All session data (job title/company, evidence with `evidence-N` IDs, transcript, suggestions) is JSON-encoded in the user message; the system prompt holds only instructions, including that the data is untrusted and that no hiring assessment is allowed. The transcript keeps the latest lines within 24,000 characters (each line ≤ 2,000); chat history itself holds the last 40 turns.
- **Validation.** The reply must be one JSON object matching `InterviewReviewSchema` (zod): bounded lists and strings (clipped), unknown keys stripped, evidence IDs filtered to the session's evidence. An invalid reply gets one repair request that quotes the issues and the previous output as data; a second failure is `failed` / `invalid_output`.
- **Cost controls.** At most two model requests (generation + repair), each checked against `Budget.canGenerate()` first and charged with `recordUsage` like any generation. Requests use a 1,500-token output cap (`maxOutputTokens`, passed per request; the OpenRouter adapter keeps one client per model and cap, Groq sends `max_tokens`) and share a 30-second deadline (`timeoutMs` per request overrides `OPENROUTER_REQUEST_TIMEOUT_MS`). An exhausted budget or an empty transcript is `skipped` without a model call. No automatic retries beyond the single repair.
- **Logging.** Metadata only (session ID, line counts, outcome); never transcript or review text.

## Sessions and resume

- **Lifecycle.** `websocket/handlers/connectionLifecycle.js` binds each authenticated socket to a session held by `services/session/sessionManager.js`. A connection creates its session lazily on its first frame, unless that frame is `{ "resume": ... }`. Session IDs come from `services/session/sessionId.js`: 128 random bits as base64url (22 characters), replacing the old time-based ID. Redis key names are unchanged. Each session records its owner, the JWT `app_id` and `device_id` claims.
- **Opt-in.** Sessions whose client did not list `"resume"` in `context.capabilities` are purged on socket close exactly as before. `contracts/interviewContext.js` reads the flag with `requestsSessionResume` (and the `debrief` flag with `requestsDebrief`); `parseClientCapabilities` still returns only the generation capabilities (`{ stream, actions }`).
- **States.** `active` → `disconnected` (socket closed, resume-capable) → `active` (resumed) or `expired` (after `RESUME_WINDOW_MS`, default 120,000 ms; `0` turns the window off). `{ "end": true }` → `ended`. An owner (JWT `app_id` + `device_id`) holds at most `MAX_DISCONNECTED_SESSIONS_PER_OWNER` (default 3) disconnected sessions; when another disconnects, the owner's oldest one is purged immediately. Ended and expired sessions are purged with the same calls as before (chat history, context, budget) and forgotten. On disconnect, `StreamManager.pause()` aborts the in-flight intro and live generation, drops queued questions, and stops the Deepgram streams without closing the session; the next audio chunk reopens them. An interrupted live generation is reported as `failed` with `reason: "disconnected"` and is never re-run, so a resume never repeats a paid request.
- **Ownership.** A resume whose JWT owner differs from the session owner receives `{ "error": "resume_rejected" }`. The session is left as it is and the socket stays open for a new session. Unknown, ended, expired, or non-resumable IDs receive `resume_expired`. A resume for a session still attached to another socket takes it over and closes that socket with `4002 session_resumed_elsewhere`.
- **Sequencing and replay.** `services/session/sessionChannel.js` stands in for the socket that `messageHandler` and `StreamManager` write to. Without resume it forwards frames unchanged. With resume it adds a monotonically increasing `seq` to every frame and keeps committed frames (transcripts, `ai_reply` results, errors; never `thinking`, deltas, or `interim` frames) in a bounded replay buffer (`services/session/replayBuffer.js`: last 200 messages, 256 KiB). The buffer accepts frames while no socket is attached and replays those after `lastSeq` on resume.
- **Single instance only.** Sessions and replay buffers live in process memory. Running more than one backend instance needs a shared replay/session store (for example a capped Redis stream per session) and sticky routing first, and a restart loses all resumable sessions. Owner-scoped limits on the number of disconnected sessions are not implemented yet; the window bounds how long each one is kept.

Protocol details are in [the WebSocket contract](protocols/websocket.md#resumable-sessions).

## Interim transcripts and utterance deduplication

- **Interim lines.** `DeepgramService` emits an `interim` event for every non-empty Deepgram result: the utterance's finalized segments so far plus the current hypothesis. When an utterance ends without any final text it emits an empty `interim` to end the line. `StreamManager` forwards these only when the latest accepted context listed `"interim"` (`parseClientCapabilities()` returns `interim`), as `{ interim: { speaker, text } }`. `services/transcription/interimTranscripts.js` bounds the text to 500 characters (newest kept) and throttles per source (`createInterimThrottle`, 200 ms, newest text wins, unchanged text not resent; `interimIntervalMs` is injectable for tests). Interim text never goes to `ChatHistory`, the classifier, or the generation scheduler, and nothing is logged about it. A final utterance, `pause()`, `closeAll()`, and a capability downgrade drop any pending line and timer; `stopStreams()` also detaches the `interim` listeners.
- **Deduplication.** `services/transcription/utteranceDeduplicator.js` checks each transcribed final utterance before it is stored: a repeat of the same source's previous final within 3 s (`UTTERANCE_DEDUP_WINDOW_MS`; `dedupWindowMs` injectable) whose normalized text is identical, or that repeats at least its last three words, is dropped. A repeat extends the window. The drop is logged at debug level with the source and character count only. Typed interviewer questions bypass the filter. If an interim line was shown for the dropped utterance, the client receives an empty `interim` frame to clear it.
- **Tests.** `test/interimTranscripts.test.js`, `test/utteranceDeduplicator.test.js`, and the replay fixture `test/fixtures/sessions/en-interim.json` (interim frames on both channels, an exact and a repeated-tail duplicate final, an abandoned interim line, nothing after end).

## Authentication

`POST /auth/token` is rate-limited per client IP (`AUTH_RATE_LIMIT_PER_MINUTE`, default 20, fixed 60-second window in Redis under a hashed `rl:auth-token:` key) and answers `429 { "error": "rate_limited" }` with `Retry-After`; if Redis errors the limiter fails open and logs a warning. Behind a reverse proxy set `TRUST_PROXY_HOPS` (the Compose stack uses `1` for Traefik) so the client IP, not the proxy's, is used.

Tokens are signed with issuer `call-backend` and audience `call-electron`.

### WebSocket tickets

The long-lived JWT no longer has to authenticate the socket. Code: `services/auth/wsTicketStore.js`, shared by `createApp({ wsTickets })` and `startWebSocketServer({ wsTickets })` (wired once in `index.js`).

- **Issue.** `POST /ws-ticket` verifies the `call_token` cookie like `/auth/me` (and that its `app_id` is `APP_ID`), then returns `{ "ticket": "<43 base64url chars>", "expires_in": 30 }` with `Cache-Control: no-store`. The ticket is 256 random bits; Redis stores only `wsticket:<sha256(ticket) hex>` → `{ app_id, device_id }` with `EX WS_TICKET_TTL_SECONDS` (default 30, 1–300). No cookie → `401 no_cookie`, a bad cookie → `401 invalid_cookie`, a Redis failure → `503 ticket_unavailable`. Requests are rate-limited per installation (`WS_TICKET_RATE_LIMIT_PER_MINUTE`, default 30; fixed 60-second window under a hashed `rl:ws-ticket:` key, keyed by the verified `device_id`) → `429 rate_limited` with `Retry-After`; the limiter fails open like the token limiter.
- **Consume.** The WebSocket server reads `?ticket=` during the handshake (`verifyClient`) and deletes it atomically with `GETDEL` (Redis ≥ 6.2), so a ticket opens at most one connection even under concurrent handshakes. The stored claims become the connection owner exactly as JWT claims do (`ws.user = { device_id, app_id }`), so session ownership and `resume` checks are unchanged. Unknown, malformed, expired, reused, or foreign-app tickets close with `4001 auth_failed`; a Redis failure while consuming closes with `1011 auth_unavailable`. When `?ticket=` is present the cookie and `?token=` are ignored, so a bad ticket never falls back to the JWT.
- **Compatibility flag.** With `WS_ALLOW_COOKIE_AUTH=true` (the default) a connection without a ticket is still authenticated by `?token=` or the `call_token` cookie, which verifies audience, issuer, application ID, and device ID as before (no credential → `4001 auth_required`, invalid → `4001 auth_failed`). With `false`, only tickets are accepted and any other connection closes with `4001 auth_required`.
- **Turning cookie auth off.** Desktop builds that request tickets fall back to the cookie only when the server has no ticket route. Once every supported desktop release requests tickets (and the updater has rolled it out), set `WS_ALLOW_COOKIE_AUTH=false` in the deployment, then remove the cookie/`?token=` path from the socket in a later release.
- **Logging.** Tickets and tokens are never logged; failures log only a fixed reason or an error code.

## Integrations and data

`DeepgramService` uses the `nova-3` live model with `linear16`, 48 kHz mono audio, French language, interim results (forwarded only to `interim`-capable clients, see above), VAD, and utterance boundaries. `StreamManager` limits generated replies to one at a time and uses an 800 ms cooldown and a 12-second model timeout.

Redis stores JSON conversation entries in a list and context as JSON. Groq uses `openai/gpt-oss-120b`; prompt construction is in `services/ai/promptBuilder.js`. Prompts and responses should remain concise and French unless product requirements change.

See [the WebSocket contract](protocols/websocket.md) before changing client or server message handling.
