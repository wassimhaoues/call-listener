# Desktop Client

The desktop application lives in `Call_Listener_Frontend/v-0/`. It combines Electron, Vite, React, React Router, Tailwind, and Framer Motion.

## Main process and security

`main.js` creates the window and tray, performs authentication, selects platform capabilities, controls auto-updates, and delegates all audio lifecycle work to a platform-audio adapter (see below). It loads the renderer on a neutral `/connecting` screen before authenticating, then navigates to the result route. The token request (`AuthManager`) has a 10 s wall-clock timeout (`AUTH_REQUEST_TIMEOUT_MS`, injectable as `requestTimeoutMs`), and the model catalog request has its own 5 s deadline; a timeout rejects with `code: "ETIMEDOUT"`, which `services/authFailure.js` classifies as `server_unreachable` (or `offline` when `net.isOnline()` is false). `getWsUrl()` invokes `auth:getWsUrl`, which calls `AuthManager.makeSignedWsUrl()`: it requests a single-use ticket from `POST /ws-ticket` with the main-process cookie (5 s deadline, `WS_TICKET_REQUEST_TIMEOUT_MS`; a `401` refreshes the token once and retries) and returns `wss://<host>/ws?ticket=<ticket>`. Because the socket hook asks for a fresh URL on every connection and reconnect attempt, each attempt uses a new ticket. Only when the server has no ticket route (`404`, or `426` from an older deployment whose proxy sends every `/ws*` path to the WebSocket server) does it return the plain `/ws` URL authenticated by the `call_token` cookie; any other failure rejects, and the hook reports it as a failed (or retried) connection attempt. `preload.js` exposes only the explicit `getWsUrl()`, `getPlatformCapabilities()`, `getModels()`, `generatePreparationBrief(context)`, and `getDiagnostics({ interviewerSource })` methods. `getModels()` asks the main process to call the backend `GET /models` with its own `call_token`; the renderer receives only model IDs, names, and availability (or `null` on failure), never the token. The Interview Settings step shows the catalog as an "AI model" picker: unavailable models are listed but disabled, the server default is used when nothing is chosen or the catalog cannot be loaded, and a saved choice that is no longer offered is cleared with a visible notice rather than silently replaced. `generatePreparationBrief(context)` invokes the `preparation:brief` IPC handler, which calls `AuthManager.fetchPreparationBrief()` (backend `POST /preparation/brief` with the main-process cookie, 50 s deadline, `context.settings.model`/`language` forwarded). It resolves `{ ok: true, brief, model }` with only the whitelisted, length-bounded brief fields, or `{ ok: false, error }` with a known error code (`preparation_budget_reached`, `preparation_rate_limited`, `preparation_unavailable`, `unsupported_model`, `invalid_context`, …; anything else becomes `preparation_failed`). `services/security.js` restricts media permissions to the packaged page or local Vite origin, injects the development guard header, and sets a production content-security policy.

Closing the window hides it to the tray only when a tray exists (Windows, where the tray carries the routing toggle); without a tray (Linux) the close quits the app, so it is never left running invisibly with the microphone open. While an interview captures audio, the live page reports it with `setInterviewActive(boolean)` (IPC `session:interviewActive`, a boolean only): the tray tooltip and a disabled first menu entry read "Interview in progress — listening", and hiding the window mid-interview shows one system notification per interview saying capture continues. Launching the app again shows a hidden window (`second-instance`). The rules live in `services/windowLifecycle.js`.

Backend address (`services/backendConfig.js`): packaged builds connect to `callBackend.host` from `package.json` (shipped inside the app) over HTTPS/WSS on 443; set it before building installers for a different backend. Development uses the local backend, and `CALL_HOST`, `CALL_PROTOCOL`, `CALL_PORT`, `CALL_WS_PROTOCOL` and `CALL_WS_PORT` override either. The app refuses to start without a valid host.

Sign-in identity (`services/deviceCredentials.js`): the persisted random installation ID (`installation-id` in the user-data directory) plus a 32-byte random secret encrypted with Electron `safeStorage` (Windows DPAPI, macOS Keychain, Linux secret service) in `device-secret.bin`. `AuthManager` sends the secret only in the `/auth/token` body (never in a URL, never to the renderer), and the backend binds it to the ID on first use ([installation enrollment](backend.md#installation-enrollment)). An installation from before enrollment keeps its ID and enrolls. If the stored secret cannot be decrypted (app data copied from another computer, OS key reset), the app starts over as a new installation instead of locking the candidate out. When `safeStorage` is unavailable it signs in without a secret, which the backend accepts only while enrollment is optional. A rejected secret (`401 device_secret_invalid`) or `403 enrollment_required` shows the `credential` auth-error screen.

Do not enable Node integration or disable context isolation. Keep tokens in `AuthManager` in the main process. Production navigation opens external URLs through the system shell rather than inside the application.

## Renderer and routing

`src/App.jsx` uses `HashRouter`. The normal sequence is `/` (device setup), `/context` (legacy caller/user data, pending candidate/job migration), then `/conversation` (live audio). Supporting pages display connecting (before auth resolves), authentication, unsupported-OS, missing-VB-Cable, and diagnostics states. Shared page chrome and theme state are in `src/layout/` and `src/ui/UIContext.jsx`.

On `/context`, the preparation section builds a local, deterministic brief (`src/services/preparation.js`, no network). The separate **Improve with AI** button is the only path that sends preparation data to a model: on click, the page builds the same versioned context the interview uses (approved profile, skills, achievements, job offer, evidence references, settings; never the pasted CV text) and calls `window.callApi.generatePreparationBrief(context)`. The page shows a loading status, then renders the AI brief through `src/components/AiPreparationBrief.jsx` as plain React text (never HTML). Each STAR example lists its evidence IDs mapped back to the candidate's facts with `preparationEvidenceIndex()` (`A<n>` = n-th achievement, `E<n>` = n-th requirement → evidence reference) from the context snapshot that was sent. A **Show local brief** / **Show AI brief** toggle switches views. Errors (budget reached, rate limited, unavailable on the server, unsupported model, failure) are shown as an alert from `aiPreparationErrorMessage()`, and the local brief stays visible. The AI brief is not stored and is not sent to the interview session.

The conversation page captures two distinct `audioinput` devices when system capture is available. In Linux microphone-only mode it captures just the candidate microphone and clearly identifies interviewer audio as unavailable. If the interviewer device disappears during the interview (its track ends), `useAudioCapture` releases only that source and calls `onSourceLost("system")`. The page then shows an alert, swaps the interviewer meter for "Interviewer audio disconnected", and turns on the typed-question box. The microphone keeps capturing, and no interviewer speech is generated in place of the lost source. `src/worklets/pcm-processor.js` is preferred; the page falls back to `ScriptProcessor` if worklets fail. Both paths emit PCM16, mono, 48 kHz chunks to the backend. UI device and legacy context selections are stored in localStorage.

`src/pages/Conversation.jsx` only composes and renders the live workspace. Its logic lives in tested modules:

- `src/services/conversationState.js` — pure reducer for status, transcript entries, the current (latest) interviewer question, pending/thinking guidance, streamed guidance keyed by generation ID (deltas append only for the current ID; the final reply replaces them; other IDs are ignored), stale-guidance hiding, terminal failure/budget states, pause, response-action state (the shown suggestion's `kind`, the completed generation an action may target, a pending action, and the last rejection), dropped-audio counts, and one in-progress interim line per speaker (`state.interim.{interviewer,candidate}`: replaced by each `interim` frame, cleared by that speaker's final transcript, an empty interim frame, pause, any connection change, capture failure, or a new session; ignored while paused; bounded to 500 characters). Incoming server messages pass through an ordered list of handlers. `canRequestResponseAction(state)` decides whether the response actions are available.
- `src/hooks/useInterviewSocket.js` — opens the socket from `window.callApi.getWsUrl()`, sends stored context on open (adding `capabilities: ["stream", "resume", "debrief", "interim"]`), routes every socket event to one `dispatch`, applies audio backpressure, sends typed questions and response actions, and ends idempotently (also on unmount). `endWithReview()` sends `{ end: { debrief: true } }`, stops reconnecting, and resolves with the `debrief` answer (or a failure when the socket closes or nothing arrives within 45 s) before closing the socket.
- `src/components/LiveGuidancePanel.jsx` — current question, plain-text suggestion (never HTML; `SuggestionText.jsx` with `src/services/suggestionSections.js` shows the known section headings — Answer outline, STAR detail, Evidence used and the French equivalents — as fixed labels and bullet lines as lists, stripping only `**` bold markers), the suggestion kind, response actions, relevant experience, and the typed-question fallback. A completed suggestion longer than three sentences (`src/services/suggestionPreview.js`; each non-empty line counts as at least one, line breaks kept so STAR outlines stay readable) shows its first three sentences and a **Show more** / **Show less** button (`aria-expanded`, `aria-controls`). A new suggestion starts collapsed; streamed partial text is always shown in full. The Alt shortcuts keep working while the toggle has focus.
- `src/hooks/useAudioCapture.js` — getUserMedia, AudioWorklet (or `ScriptProcessor` fallback) graph, meter levels, flush, and idempotent release of tracks and the `AudioContext`.
- `src/services/audioCapture.js` and `src/services/interviewMessages.js` — pure capture helpers and client message encoders.
- `src/components/TranscriptLog.jsx` — text-only transcript with near-bottom auto-scroll. In-progress interim lines ([protocol](protocols/websocket.md#interim-transcripts)) follow the final entries, labelled "Interviewer (speaking…)" / "Candidate (speaking…)", italic, dimmed, and ending in "…"; growing interim text also follows the bottom.
- `src/services/debriefState.js`, `src/services/debriefMarkdown.js`, `src/components/DebriefPanel.jsx` — the unsaved review (below).
- `src/services/storedContext.js` — reads the saved `callContext` without throwing (missing, corrupted or non-object values read as none). The live page checks it before opening the socket or the microphone: without a version-1 context that names the candidate and the job (first run, cleared storage, a legacy context, or a Retry/reload that lands on `/conversation`), it explains why and goes to `/context` instead of starting a session with nothing to ground guidance in.

### Response actions

Under the suggested answer, four buttons ask the backend for a different take on the current suggestion ([protocol](protocols/websocket.md#response-actions)):

| Button | Shortcut | Result |
| --- | --- | --- |
| Regenerate | Alt+R | A fresh answer to the same question. |
| Shorter | Alt+S | The answer as at most three speakable sentences. |
| More detail | Alt+E | Evidence-grounded STAR detail. |
| Clarify | Alt+C | Clarifying questions to ask the interviewer. |

The buttons apply only to a completed suggestion for a live question (not the introductory suggestion). They are disabled while a suggestion is being generated or an action is pending, while paused, while disconnected or reconnecting, after a failure, and once the interview budget is reached. Shortcuts use the physical key (`event.code`), so they work on layouts where Alt+letter types a character, and they are ignored while focus is in a text field (for example the typed-question box) or when Ctrl, Shift, or Meta is held. A badge names the kind of the shown suggestion ("Shorter answer", "Clarifying questions to ask", …). A rejected action (for example rate limited or no longer current) is explained in plain text below the buttons; a stale rejection disables the buttons until the next answer. Buttons show a visible focus ring (`.btn:focus-visible`).

### Stop and review

The top bar has **Pause**, **Stop and review**, and **Stop** (ordinary buttons, reachable with Tab and activated with Enter or Space). **Stop** behaves exactly as before. **Stop and review** follows the same order (flush the final audio batch, send it, end, release capture) but sends `{ "end": { "debrief": true } }` and keeps the socket open until the backend answers ([protocol](protocols/websocket.md#unsaved-debrief)). The live view is replaced by the review panel, which shows "Preparing your review…" and then either:

- the review: questions covered (with what the candidate said and the evidence used, named by requirement), strengths, topics to improve, and an editable follow-up draft (a textarea; it is never sent anywhere), or
- a plain-text explanation when the review was skipped (budget spent, nothing transcribed) or failed (including no answer within 45 s or a closed connection).

In every result state the candidate can also write **Your notes**, a self-review textarea (at most 8,000 characters, held only in memory). The notes are exported with the review, or on their own (with "No AI review was available") when the review was skipped or failed; Export appears then once notes are non-empty.

Everything is rendered as text nodes, never HTML. `debriefState.js` is the pure reducer (`idle` → `preparing` → `ready`/`failed`/`skipped`; edits to the draft and the self-review notes; discard) and bounds what the server sent.

**Export as Markdown** builds the file in the renderer with the pure `buildDebriefMarkdown()` (all review text backslash-escaped so it stays literal Markdown; the draft goes in a fenced block) and saves it through a `Blob` and a temporary `<a download>` link, so Electron shows its save dialog. No IPC is involved. **Discard** (or **Cancel** while preparing, **Back to setup** after a failure) forgets the review and returns to setup.

Nothing is stored: the review lives only in page state, never in localStorage or the main process, and the backend purges the session right after sending it. The panel says so, and the exported file is the only copy.

## Platform audio adapter

`services/platformAudio/index.js` exports `createPlatformAudio({ platform, capabilities, logger, fs, windows })`, which picks an adapter from `services/platformCapabilities.js` output. `main.js` no longer branches on `process.platform` for audio; startup, the tray, `powerMonitor` suspend/resume, quit cleanup, and the diagnostics IPC all go through the adapter:

| Adapter | Chosen when | Behavior |
| --- | --- | --- |
| `windows-vb-cable` (`windowsAdapter.js`) | capability strategy `vb-cable` | Wraps `AudioRouteManager` unchanged. `prepare()` resolves SoundVolumeView through the injected `ensureTools` UI hook; `ensureReady()` recovers a dirty state, detects VB-Cable, enables routing, and sets the cable as default, or returns `needs-device` (main shows `/novbcable`, offers the installer, and polls). Redundant enable/disable calls are skipped, routing changes are serialized, `gracefulExit()` runs once, and routing is never re-enabled after exit. |
| `linux-app-streams` (`linuxAdapter.js`) | Linux | Runs no commands and never changes OS routing. Stops only streams registered with `trackStream(id, { stop })`. Reports microphone-only capture until PipeWire desktop capture (L2) is qualified. No tray is created because there is no routing to toggle. |
| `unsupported` | any other OS | Inert; main shows `/unsupported`. |

### Linux interviewer source (monitor)

On Linux, `getPlatformCapabilities()` adds `systemAudio.selectableSource: "monitor-source"` (Windows stays `strategy: "vb-cable"` and is unchanged). With that capability, Setup does not request media permission when it opens. It lists audio inputs and splits them with `partitionAudioInputs()` from `src/services/monitorSources.js`: labels containing "Monitor of …" (including "Default - Monitor of …" and "Remapped Monitor of …") or a raw `*.monitor` source name count as monitors, and everything else is a microphone. Monitors are offered only in the optional **Interviewer audio (system output)** panel (`src/components/InterviewerSourcePicker.jsx`), never as microphones.

- Labels hidden (no permission yet): the panel shows **Allow audio access**. It runs one `getUserMedia({ audio: true })`, stops the tracks at once, and lists the devices again. If permission is denied, the panel says so and the candidate stays in microphone-only mode.
- **Refresh** lists the devices again. A choice whose device is gone falls back to None.
- The default is always **None — type the interviewer's questions**. A monitor saved earlier is not restored automatically.
- When none is found, the panel explains that many Linux setups do not show monitor sources to apps and that translated names are not recognised yet.

On **Next**, a chosen monitor is stored as `sysId`, with `systemAudioEnabled=true` and the generic label "Interviewer audio (system output)". Conversation captures it as the `system` (interviewer) source through the same constraints and PCM path as VB-Cable, and the microphone stays `mic`. Setup also stores `interviewerSource` (`monitor-source`, `vb-cable`, or `none`); the diagnostics page sends only this enum.

Exposure caveat: Chromium's PulseAudio backend (which PipeWire serves through pipewire-pulse) leaves real monitor sources out of `enumerateDevices()`. A local probe with Electron 44 and PipeWire 1.0.5 listed none, so on a stock setup the panel shows "No system output monitor sources are visible". A monitor appears only when the system exposes it as a regular input (for example "Remapped Monitor of …" from a `module-remap-source` the user created). Call Listener never creates one. Locale caveat: the sound server translates "Monitor of". Only the English description and the locale-independent `.monitor` name are recognised. Capture from an exposed monitor is unit-tested with mocked media devices only; see the [Linux support plan](plan/08-linux-support.md).

`describe()` returns a renderer-safe snapshot (kind, state, routing flag, error code). It never includes paths, device IDs, or raw error messages.

## Diagnostics screen

`/diagnostics` (activity icon in the header, available on every screen including Connecting) shows OS family and architecture, display server (X11/Wayland from `XDG_SESSION_TYPE`, `WAYLAND_DISPLAY`, or `DISPLAY`; `n/a` outside Linux), capture strategy, system audio route availability, the interviewer source kind chosen in Setup (`getDiagnostics({ interviewerSource })` forwards only that enum; `buildDiagnostics()` maps known kinds to "Monitor source selected", "VB-Cable", or "None (typed questions)" and anything else to "Not chosen yet"), adapter kind and state, routing state (Windows), app and Electron versions, and actionable issues. The main process builds it with the pure `services/diagnostics.js` `buildDiagnostics()`, which whitelists fields, accepts only short version/enum tokens, and maps error codes to fixed copy. It must never carry hostnames, user names, installation IDs, user paths, or IP addresses; `test/diagnosticsBuilder.test.js` enforces this.

## Windows audio routing

`AudioRouteManager` uses bundled SoundVolumeView to detect VB-Cable, save the prior playback device, enable “listen to this device,” and restore settings on a clean exit. It writes recovery state to Electron user data and starts `watchdog.js` so a crashed app also restores the device. VB-Cable installation requires elevation. Test routing carefully: it changes the Windows default playback device.

## Linux baseline

Linux is an unqualified development path: microphone-only by default, with an optional monitor source the candidate picks as interviewer audio (see above). It must not invoke VB-Cable installation, SoundVolumeView, audio routing, or the Windows watchdog; the `linux-app-streams` adapter guarantees this structurally. PipeWire desktop audio, real-session validation of the monitor-source path, packaging, and real Electron startup validation remain tracked in the [Linux support plan](plan/08-linux-support.md).
